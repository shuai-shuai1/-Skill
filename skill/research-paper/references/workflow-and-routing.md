# 工作流与模式路由

## 目录

- 总原则与路由顺序

## 总原则

先判断用户要解决的决策，再决定产物。不要因用户说“写论文”就直接生成全文。

## 路由顺序

1. 判断是否已有明确研究问题、正式材料和目标产物。
2. 判断任务是规划、审计、写作、绘图、审稿修订还是投稿终审。
3. 判断是否涉及真实数据、代码、日志、外部文献或参考图。
4. 选择一个主模式，列出必要的串联模式。
5. 只加载该模式需要的参考文件。

## 模式决策

### `plan`

满足任一条件时使用：研究问题不够明确；材料零散；用户不知道如何组织论文；实验已经完成但论文主线未确定。

步骤：

1. 建立 Paper Brief。
2. 用一句话表达研究问题、中心主张和最重要的证据。
3. 识别材料缺口和不可更改项。
4. 选择章节结构并分配每章任务。
5. 形成最小下一步，不生成未经确认的全文。

### `evidence-audit`

用于判断“现有材料能否支持某个论文结论”。这是模糊任务的默认入口。

步骤：

1. 建立 Evidence Ledger。
2. 建立 Claim-Evidence Matrix。
3. 区分正式实验、smoke、日志、推导、理论和 synthetic 数据。
4. 对每个主张给出 `SUPPORTED`、`PARTIAL`、`UNSUPPORTED` 或 `CONTRADICTED`。
5. 输出阻断项和最小补证据动作。

### `experiment-to-paper`

用于从仓库、训练配置、运行日志、报告和结果文件生成论文方法与实验内容。

步骤：

1. 读取项目级规则和已有实现。
2. 固定数据、代码、配置、随机性和运行身份。
3. 核对 baseline、公平比较和数据泄漏风险。
4. 形成实验契约与结果台账。
5. 只将已完成、已验证的运行写为结果。

### `write-revise`

用于从零搭稿、重构、局部改写或精修。

步骤：

1. 冻结主线、数据口径和修改范围。
2. 先处理结构和证据，再处理语言。
3. 局部修改时保留未授权区域。
4. 给出成品、关键修改、保留项和残余风险。

### `figure`

用于生成数据图、结构图、系统图、流程图或参考图重绘。

步骤：

1. 填写 Figure Specification。
2. 判断数据图、矢量结构图、位图生成还是 PPT 高保真复现。
3. 先锁结构、数据和版权边界，再选择工具。
4. 交付可编辑源、输出图、图注、数据来源与 QA。

### `review-response`

用于审稿意见解析、修改计划、正文修改和回复信。

步骤：

1. 将复合意见拆成原子项。
2. 标记严重度、影响章节和证据需求。
3. 对每项选择接受、部分接受、有依据地不同意或无法完成。
4. 修改正文后再写回复，记录页码或行号。

### `pre-submit`

用于最终交付或投稿前审计。

步骤：

1. 运行证据、文稿和图件脚本检查。
2. 人工检查科学边界、引用和视觉质量。
3. 区分阻断项、警告项和建议项。
4. 阻断项未关闭时，不宣称“投稿就绪”。

## 检查点

- Checkpoint A：研究问题和中心主张得到确认。
- Checkpoint B：章节结构和关键主张得到确认。
- Checkpoint C：正式结果身份得到验证。
- Checkpoint D：图件数据与正文一致。
- Checkpoint E：投稿前阻断项为零。

只在 Checkpoint A 或 B 会改变整篇方向时暂停请求确认；其余不影响方向的细节可明确假设后继续。

## 状态表达

使用诚实状态：

- `READY`：必要材料和验证齐全；
- `PARTIAL`：已完成一部分，但缺少关键证据；
- `BLOCKED`：缺少用户选择、外部运行或必要权限；
- `DRAFT`：仅为待验证草稿。

不要把“脚本能运行”“smoke 通过”“图看起来正确”写成论文结论已经成立。
